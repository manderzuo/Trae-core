# Seedance 缺档预冻结与自动报价校准设计

日期：2026-09-29。状态：书面设计，待审阅；本文件不代表代码已经修改、测试通过或公网已经部署。

## 1. 目标和确定的规则

用户已确定：遇到没有参考报价档的受支持视频请求，采用“15 秒、720p”基准作临时预冻结，允许任务提交并获取真实账单。真实账单到达后立即按请求及 Key 校对，多退少补，并自动记录新规格。不能冻结整个 Key 余额，不能因缺少精确报价一直阻断正常测试。画面比例不是本项目 Seedance Fast 480p/720p 的报价维度。

此改造涉及本机 AI Work 助手的报价选择和公网 Core 的失败信息保存，按跨组件设计处理。助手代码归 trae-maker，Core 代码归 Trae-core；MCP 不修改。只改上述链路，不调整已有账号并发分流算法，不开启已关闭的监控计划，不清理历史账务。

“15 秒、720p 是理论最高扣费”目前只能作为用户选定兜底的依据，不能作为已经验证的上游价格上限。带参考视频等输入可能有独立收费因素；实际扣费高于兜底时仍必须如实入账。

## 2. 已核对的现状

- `bridge_planner::video_profile` 保留执行比例，将报价比例统一为 16:9，并区分图片数量、视频数量。
- `bridge_reference::owned_reference_seconds` 从拥有者绑定的实际 MP4 读取保守时长并向上取整，不能信任客户端或语言模型声明的素材时长。
- 现有邻近档查找要求相同分辨率、参考数量及参考秒数，缺少相同参考类别就无法兜底。
- `bridge_prepared::confirmed_video_prices` 已从持久化、核验后的真实账单自动提取价格，按上游账号隔离，读取最近 7 天成功视频的正数最终回执。相同规格取较高实际值，重复回执及冲突有现有保护。
- 当前本机策略配置有 480p/5 秒/6 秒参考视频档，没有有效的 720p/15 秒统一兜底条目。代码中的测试数字不能代替已核验生产报价。
- Core 的任务查询在未形成视频步骤时将失败统一显示为 `budget_not_sent`；`reflect_failure` 忽略传入的具体错误码。这会丢失实际拒绝原因。

因此选择扩展现有报价链路及回执学习，不新建独立资金账本，不让语言模型生成价格或改写代码。

## 3. 报价优先级

按以下顺序选择，取到有效档后不再叠加其他档的金额：

1. **同规格真实账单**：使用当前上游账号下该规格近期可信实际扣费的较高值，经现有安全余量规则形成预冻结额。
2. **有效的同规格管理报价或受支持的原生估价**：保留现有校验。证据已经过期、冲突、身份不匹配或上游明确拒绝时不能当作可信估价。
3. **同参考类别向上取档**：模型及分辨率相同，图片/视频数量相同；生成时长不小于请求时长，视频参考总时长不小于实测参考时长。优先选可覆盖请求的最接近档。安全余量只加一次。不将短参考视频的价格直接当作长参考视频价格。
4. **统一兜底**：没有以上可用档时，对于本次明确开放的 Seedance Fast 480p/720p、4–15 秒及已通过限制检查的参考输入，使用管理员启用的 720p/15 秒临时风险额度。

这里的缺档兜底只处理“没有精确价格”，不绕过素材所有权、实际时长、格式、大小、个数、鉴权、Key 状态、资金余额、上游容量、账单冲突及恢复状态等检查。未知模型或不受支持的输出规格仍明确拒绝。

### 统一兜底配置

新增独立的管理员配置项，包含 `enabled`、`model_family`、`baseline_resolution=720p`、`baseline_duration_seconds=15`、`hold_microcredits`、`policy_version`、证据来源和有效期。

- 金额从已核验的 720p/15 秒账单或已捕获并核验的上游估价计算，或由管理员明确给出临时风险额度。不从客户端传入，不直接复用过期策略。
- 如果基准存的是实际扣费，沿用现有 10% 余量、向上取整到一积分的规则；配置保存的是最终预冻结额，不再二次加余量。
- 本次用户接受的是统一风险兜底，因此在缺少参考档时不额外要求先取得每种参考输入的专属报价，也不暗中冻结全余额。
- 兜底有自己的明确有效期。实施阶段将金额、来源及有效期写入发布审计记录；未取得有效基准前，不宣称配置已可用。
- 若无法核验基准、基准过期或管理员关闭，则返回清楚的兜底不可用错误，不编造价格。
- 预冻结仍须同时通过 Core Key 可用积分和上游账号容量检查。额度不足就明确拒绝，不缩小预冻结去掩盖不足。

兜底预算使用标记 `fallback-risk-720p15s-v1`，证据等级为临时风险估算。真实请求仍按原来的生成秒数、分辨率、比例和参考素材提交，不改成 15 秒、720p，也不把这个请求的报价身份改成兜底基准身份。

## 4. 自动加入模板

正式报价身份保留：上游提供方/模型族、账号计价范围、生成秒数、分辨率、图片数量、视频数量、实测参考总秒数。比例只保留在任务执行信息中，不拆报价档。全视频参考与尾帧参考保留实际输入区别，不能混用报价。

继续用现有核验回执作为持久化校准事实：

1. 确认该视频执行成功，并有正数实际积分回执。
2. 核对 request_id、core_key_id、budget_id、account_ref、bridge_instance_id、session/task 及回执证据绑定；拒绝用上游账号总消耗直接猜该任务价格。
3. 保留预冻结时封存的实际请求规格。从中取得本次规格，不能从基准兜底档复制规格。
4. 回执持久化后，该规格即可被下一次报价读取。逻辑上新增正式模板条目，不需要改源码、手动改 JSON 或建立第二套金额权威。
5. 条目能追溯实际值、样本数、最近观测时间、账单证据及原始策略版本。若需要界面列表，采用只读派生视图，不另行维护余额。

模板价格暂保持现有最近 7 天有效观测的较高值；事实记录永久保留，重启可恢复。没有近期样本就回退到有效兜底，不能将过期观测伪装为当前准确报价。账号计价身份不一致时不自动共享“精确报价”，但其他账号同样可使用管理员明确启用的统一兜底。

重复回执不重复增加样本或扣款；冲突/未知/未收费失败/身份不匹配的回执不进入模板。较低的新样本不能直接覆盖仍有效的较高样本。模板读取或展示失败不得回滚已经确认的真实结算，不得把校准重试变成生成重试。

## 5. 结算与正常使用

- 辅助模型与视频仍按各自步骤记录、冻结和结算，不把辅助费用冒充视频费用。
- 每笔并发请求有自己的预冻结。账单归属不靠提示词，也不因同 Key 在多个客户端使用而混合。
- 获取明确执行终态后及时释放执行并发名额；未确认的金融预占独立保留。账单晚到不能继续占执行名额，也不能先退款造成重复花费。
- 收到可信账单后立即走现有事务结算与回执事件链，释放差额；重复回执幂等。设计验收目标为回执已被系统读取后 5 秒内完成 Core 可用额度更新，另行测量，不把这个目标描述成上游账单返回保证。
- 实际扣费超出预冻结时如实记录差额，按既有不足/欠额保护处理受影响 Key 和上游容量。不得把真实扣费截断到兜底值。新真实值参与该规格下一次校准，哪怕超过 15 秒基准。
- 如果上游长时间没有可核验回执，保留这笔未知预占并显示待核对状态；不冻结额外全余额，不伪造实际账单。

## 6. 保存具体错误，便于客户端和监控定位

确定性提交前失败必须在执行收尾时保留允许公开的具体错误码、HTTP 状态和阶段，并绑定父 request_id，使用现有 request result/审计存储。金融状态仍按真实辅助/视频步骤展示。

- Core 的状态查询、SSE 反馈、失败重放读取同一条错误事实，不再统一覆盖为 `budget_not_sent`。
- 同一个失败请求保留首次明确原因，幂等读取不覆盖；并发前后台收尾的错误写入与执行终态一致。
- 错误写入只接收明确允许公开的错误码/状态，文字由安全映射产生，不保存含凭据、原始上游响应或用户完整提示词的错误文本。
- 历史错误码为空的请求仍显示“具体原因未保存”，不能根据当前报价配置倒填旧任务原因。
- 需要重试时创建新的请求身份，由用户发起；读取错误不能自动重新生成或重新扣费。

## 7. 实施归属与验收

AI Work：主要调整 `bridge_planner` 的风险兜底配置、选择优先级及向上参考时长取档；核对 `bridge_prepared` 的原始规格保存和回执学习。价格派生不会写回修改原金融事实。

Core：补齐确定性失败原因的持久化与任务查询/SSE/幂等重放的一致反馈；保留现有执行与金融状态分离以及资金隔离。

实施时需要覆盖的回归及真实验收：

1. 本次类似的 10 秒/720p/9:16、约 10.11 秒参考 MP4 缺档请求，成功选择兜底且完整保留原规格；不因精确参考档缺失返回报价 503。
2. 480p/720p 全部受支持秒数及不同比例的缺档；未知模型/1080p/非法时长不借兜底放行。
3. 新规格真实账单完成后，同账号下一次请求按该规格学习值预冻结；重启后仍有效，比例变化不另建价格档。
4. 重复、冲突、零扣费失败、晚到、错误 Key/预算/账号关联账单不能污染模板或造成重复扣款。
5. 同 Key 双客户端并发、不同 Key 并发分别关联素材、请求和账单；结算释放只影响自己的预占。
6. 执行结束但回执晚到时名额可释放；真实结算后测量 Core 可用额度更新延迟。
7. 实际低于、等于、高于兜底，以及 Key/账号容量不足、基准过期、基准关闭场景。
8. 确定性失败的首个响应、查询、SSE 和重放能够显示具体原因；历史空原因不会被猜测补写。
9. 用户授权实施后，以新的唯一请求进行少量真实付费参考视频验收，核对视频、素材绑定、真实扣费、额度释放和学习结果；不重放此前失败的付费任务。

本次仅交付设计，没有新增测试运行、付费请求、程序重启、数据库变更、Git 推送或生产部署。
