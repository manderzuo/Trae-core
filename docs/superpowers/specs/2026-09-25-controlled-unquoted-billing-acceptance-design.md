# 受控无报价计费验收设计（方案 B）

日期：2026-09-25

状态：设计稿；尚未实现、部署或开启生产闸门。

适用仓库：`Trae-core` 与 `trae-maker`（AI Work）；MCP 不在本次修改范围。

## 目标与边界

用户已选择方案 B，以现有“周”普通 Key 完成一次受控的真实公网 Seedance 链路验收，包括 Core 鉴权、DeepSeek 文字辅助、参考素材、Seedance 视频提交、任务观察、MP4 获取及按两个独立真实回执结算。通过后再决定是否扩大到其他 Key；不得把这次验收开关误当作长期无限制生产方案。

本方案承认当前 AI Work 无法给出调用前可核验的单任务积分上限。对受控 Key 使用其全部可用积分作为**授权持有额**，不是上游价格承诺。实际扣费可能超出该 Key 余额；Core 必须记录真实超额、冻结该 Key 并提示管理员，不得声称能够硬性防止上游超支。其他 Key 和普通无报价请求继续失败关闭。原先要求可信最高报价的方案 A 仍是长期无人值守开放的目标，不被本次诊断豁免替代。

## 已核对现状

- AI Work 的桥接报价端点仍明确返回 `quote_unavailable`；Core 正常 `active` 视频模式及普通文字模式因此不能放行无报价付费请求。
- Core 现有 `diagnostic_once` 可以按 Key 与请求哈希领取一次性视频准入，按 Key 全部可用额度预占，任务完成后查询请求级真实回执。
- Seedance Chat 的一次性路径当前先执行、结算 DeepSeek 子请求，再为视频父请求预占。若第二步失败，辅助已产生费用，不能将诊断路径简单改为常开。
- 本地现有 `video_billing` 24 项及 `per_key_real_settlement` 10 项模拟测试通过；这证明现有单请求回执、重复回执与部分断线恢复保护可复用，不证明整次复合操作已安全，也不等于真实公网验收。

## 准入与账本

1. 管理员只给指定的现有普通 Key 开启受控模式；启用、停用和每次使用均记录审计。受控模式仅允许一次运行中的父视频操作（含它的文字辅助子请求），同一 Key 的其他新付费请求不得占用这笔授权。其他 Key 的配额与请求不受此模式改变。
2. Core 在任何付费辅助调用之前完成鉴权、scope、幂等、模型/视频参数、素材归属和输入大小校验；读取新鲜的 AI Work 上游积分快照并检查全体 Key 已承诺余额。任一检查失败，不调用辅助或视频上游。
3. Core 在一个原子事务中创建父操作记录、Key 独占执行租约及该 Key 全部可用积分的操作级持有。持有金额不是报价；持久化明确标记 `unquoted_controlled`。并发请求只能有一个事务成功。客户端重试先按原有幂等/规范化请求规则回放，不能创建第二次操作或新的上游调用。
4. 辅助子请求与视频父请求分别持有唯一 Core `request_id`，关联同一操作和本地不可变 `key_id`。子请求与父请求从同一操作级持有中分账，不得各自再次预占 Key 全额；已核验的辅助实际费用先从共同持有中扣除，剩余持有继续保障视频步骤。即便辅助成功，若其回执未知、费用冲突或余额已不足，禁止视频提交并进入对账。
5. AI Work 只接收经桥接鉴权的 Core 请求编号及内部操作关联，不接收客户端自报的 Key 身份；原有 `quote_unavailable` 语义保留，不伪造可信报价。AI Work 为两个上游步骤分别持久化请求/会话或任务引用，并提供可重复查询的真实积分回执。Core 仅按本地 `request_id → key_id` 映射入账，不用 Token、固定积分或聚合余额差推算单次费用。
6. 视频提交后的排队、运行、客户端断线和普通轮询不释放持有或执行租约。只有明确终态且真实回执可核验时才结算、释放未用持有；同一回执幂等。失败但可能收费时仍等待回执。未知、冲突或服务重启时保持持有并暂停该 Key 的新付费请求，只查询/对账，不自动重发上游。
7. 若实际总费用超过持有，账本记录完整真实费用和差额，冻结该 Key，待管理员处理；不从其他 Key 偷扣、不把差额抹零。上游总余额低于 Core 对各 Key 的承诺时仍停止新增分配和付费提交。

## 对外行为与部署

- `POST /v1/chat/completions` 选择 `seedance` 时仍执行既有文字辅助和视频流程；`stream=true` 保持现有 SSE/终态回传契约，客户端断开不触发第二次生成。`POST /v1/videos/generations` 不需要辅助，但使用同一受控准入与真实回执规则。
- 参考图继续使用当前受权限和归属约束的素材接口；视频下载继续要求普通 Key 授权。服务端只能提供可下载结果，不能保证纯远程 API 自动写入任意客户端工作区。
- 受控模式默认为关闭。先在 D 盘隔离工作区做模拟与重启测试，再更新 AI Work 和 Core 的兼容版本；部署后核对版本/健康、管理员状态和 Key 余额。只有诊断记录证明没有未结清的同 Key 操作时才放行一次真实请求。真实请求不得因观察超时再次提交。
- 本次不切换干净生产数据库、不删除旧 Key 或历史账本，也不扩大权限到其他 Key。测试生成的临时构建产物按用户要求从 D 盘清理，不能误删持久视频或生产数据。

## 验收证据

模拟测试须覆盖：辅助成功但视频未提交、辅助回执未知、视频回执未知、费用超额、重复/冲突回执、同 Key 并发与不同 Key 隔离、无幂等头流式重连、客户端断开、Core/AI Work 重启、素材权限失败早于辅助调用，以及两个入口的一致性。原有普通文字、未启用 Key、非流式视频契约不能回归。

真实验收使用现有“周”Key 的一次受控视频生成，记录父/子 `request_id`、上游会话/任务引用、两个真实积分回执、Core 分别扣费、Key 剩余及可下载 MP4。若任何回执不明，保持持有并进入对账，不重复付费请求；不把仅有视频文件或仅有聚合余额变化视为计费通过。完成后默认关闭受控模式，评估长期方案 A 或下一阶段扩大范围。
